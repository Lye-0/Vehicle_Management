## 3. 次期計画で維持する仕様

### 3.1 手動紐づけした書類

現在の次の仕様を維持します。

- 車両へ手動紐づけした書類は、最終パッケージでその車両の通常書類として出力します。
- Webでも、その車両に紐づいた通常の販売・整備書類として表示します。
- 顧客にだけ手動紐づけした書類は、`vehicleId = null`の車両情報なし書類として登録します。
- 車両情報なし書類は販売・整備一覧で「ABACUS・車両なし」「車両：なし」と表示します。
- 通常のWeb画面と通常の書類作成APIから、車両情報なし書類を新規作成する機能は追加しません。
- 車両情報なし書類は、検証済みABACUSインポート経路だけが登録できます。

次期実装ではこの表示先を変更せず、自動紐づけ、手動車両紐づけ、手動顧客のみ紐づけ、おすすめ承認の判断由来を追加で保存します。

### 3.2 顧客情報がない書類と車両

- 顧客情報がない書類は、引き続きインポート候補から除外します。
- 顧客情報がない車両は、解析時点で捨てず「未確定車両」として保持します。
- 未確定車両は、補助アプリでユーザーが顧客へ手動紐づけできます。
- 最終確定時に顧客へ紐づいていない車両は、登録前パッケージへ出力しません。
- 未確定車両にしか紐づかない画像と書類も、参照整合性を確認した上で登録対象外にします。

### 3.3 書類種別、入庫区分、状態

- ABACUSから取得できる書類種別を使い、見積書と請求書を区別します。
- ABACUSから取得できる入庫区分を使います。
- ABACUSの「点検」はWeb側では「一般整備」として処理します。
- 「車検」は「車検」、「板金」は「板金」、判定できない値は既定の「一般整備」とし、警告を残します。
- ABACUSから取得できない「状態」は、書類日付とインポート基準日から決定します。
- インポート基準日の1か月前以前の書類は「完了」、それより新しい書類は「下書き」とします。
- 1か月は30日固定ではなくカレンダー月で計算し、境界日を「完了」に含めます。
- 日付が空欄または不正な書類は「下書き」とし、警告を残します。
- 再実行で結果が変化しないよう、状態計算に用いたインポート基準日を完成パッケージへ保存します。

### 3.4 未確定と明示的除外

未確定トレイとごみ箱を別の状態として扱います。

- 未確定トレイは、まだ判断されていない候補です。
- ごみ箱は、ユーザーが今回のインポートから明示的に除外した候補です。
- どちらも最終パッケージには含めません。
- 最終確定前であれば、どちらからも復元できます。
- 完成パッケージには、未確定による除外と明示的除外を別々に集計して記録します。

## 4. 共通の状態モデル

補助アプリの顧客、車両、書類は、画面上の配置ではなく永続化可能な状態として管理します。

### 4.1 候補状態

- `confirmed`: インポート対象として確定可能
- `unresolved`: 未確定トレイにあり、判断待ち
- `excluded`: ごみ箱にあり、ユーザーが明示的に除外

### 4.2 紐づけ方法

- `automatic`: 現行の厳密な自動一致
- `manual-vehicle`: ユーザーが車両へ手動接続
- `manual-customer-only`: ユーザーが顧客だけへ手動接続
- `recommended`: おすすめ候補をユーザーが承認
- `none`: 未接続

### 4.3 守るべき不変条件

- 書類は、確定した顧客へ必ず紐づきます。
- 通常の書類は、その顧客が所有する確定車両へ紐づきます。
- 車両情報なし書類だけは、顧客へ直接紐づき、車両IDを持ちません。
- 車両は、登録前パッケージへ出力される時点で確定顧客を必ず持ちます。
- ごみ箱または未確定トレイにある対象を、CSV、画像対応表、書類対応表へ出力しません。
- UIを切り替えても、候補ID、紐づけ先、紐づけ方法、未確定、ごみ箱、承認状態を変更しません。
- おすすめは自動確定ではありません。ユーザーの承認操作後だけ`recommended`として確定します。

顧客詳細画面の所有車両ブロックと同じ並びに、「車両情報のない書類」ブロックを追加します。実在しない車両レコードやダミー車両は作成しません。

実装内容:

- 顧客IDに紐づき、`vehicleId = null`かつ検証済みABACUS移行情報を持つ書類を取得するAPIを用意します。
- 顧客詳細の車両カード列に、該当書類が1件以上ある場合だけ「車両情報のない書類」カードを表示します。
- カードには販売書類件数と整備書類件数を表示します。
- カードを選択すると、顧客にだけ紐づく販売・整備書類の一覧を表示し、各書類の既存詳細画面へ移動できるようにします。
- 販売・整備タブでは車両情報を「なし」と表示し、既存の「ABACUS・車両なし」表示を維持します。
- 通常のWeb書類作成フォームと通常作成APIの車両必須検証は変更しません。
- 車両情報なし書類を車検予定、走行距離履歴、車両添付ファイルへ含めません。

受入条件:

- 顧客に複数車両と車両情報なし書類がある場合、車両カードの右側に特例カードが表示されます。
- 特例カードから販売・整備書類を開けます。
- 通常のWeb操作では車両なし書類を新規作成できません。
- `vehicleId = null`だけでは特例扱いにせず、ABACUS移行メタデータも検証します。

実装記録:

### Gate 22: 顧客なし車両の未確定トレイ対応

車両CSVの顧客名空欄行を解析対象から無条件に捨てず、独立した未確定車両候補として保持します。

実装内容:

- 車両候補生成を顧客候補への従属処理から分離します。
- 顧客名がない車両に決定的な候補IDと出典情報を付けます。
- 未確定トレイの「未確定車両」へ表示します。
- 未確定車両を顧客カードまたは顧客キャンバスへドラッグして接続できるようにします。
- 接続後は`manual-vehicle`相当の人による判断根拠を保存します。
- その車両に関係する画像、書類、識別子競合がある場合は詳細欄へ表示します。
- 顧客との接続がないまま最終確定した車両は、登録前パッケージから除外します。

受入条件:

- 顧客名空欄の車両が未確定車両に表示されます。
- 顧客へ接続した車両だけが`vehicles.csv`へ出力されます。
- 接続されなかった車両と画像は出力されず、除外件数と理由がマニフェストに残ります。
- 顧客情報がない書類は従来どおり除外されます。

実装記録:

- 候補生成で顧客名空欄の車両を捨てず、顧客ID空欄のまま決定的な車両ID・出典付きで`vehicles.csv`へ保持するようにしました。
- グラフ候補では顧客なし車両を`UnresolvedVehicleRows`として独立管理し、未確定トレイへ表示します。顧客名空欄の書類は引き続き候補から除外します。
- 未確定車両を顧客一覧または顧客キャンバスへドラッグすると、顧客IDへの手動接続を画面状態へ保存し、接続後の顧客キャンバスへ車両を表示します。解除操作で未確定トレイへ戻せます。
- 顧客キャンバス上の車両カードも未確定車両トレイへドラッグできるようにし、顧客キャンバスから除外します。元の顧客IDは保持したまま、関連書類を同時に未確定トレイへ戻し、復元時は元の顧客カードへ戻せるようにします。
- 最終パッケージでは顧客へ接続された車両だけを`vehicles.csv`へ出力し、未接続車両と対応画像を除外します。除外車両数・画像数・理由は`manifest.json`の警告、サマリー、除外車両一覧へ記録します。
- 既存の自動・手動書類リンクと顧客統合グループの処理は維持し、顧客なし車両への自動書類紐付けは行わないようにしました。
- 検証: `dotnet build apps/companion/src/VehicleManagement.Companion/VehicleManagement.Companion.csproj --no-restore`（成功）。実データでの未確定車両ドラッグ操作と最終パッケージ目視確認は次の受入確認で行います。

### Gate 23: ごみ箱と明示的除外

ユーザーが解析結果を自発的にインポート対象外へできる、ごみ箱エリアを追加します。

実装内容:

- 書類、車両、顧客候補をごみ箱へ移動できるようにします。
- ごみ箱から元の状態へ復元できるようにします。
- 顧客または車両を除外するときは、影響する車両、書類、画像の件数を確認ダイアログで表示します。
- 除外は候補ID単位で保存し、表示順やCSV行順を識別子に使いません。
- 未確定トレイ残留とユーザー明示除外を、マニフェストで別集計にします。

- ごみ箱へ移した対象がキャンバスと登録前CSVから消えます。
- 最終確定前なら復元でき、元の候補IDと出典を維持します。
- 未確定除外と明示的除外の件数が別々に表示されます。
- 親候補の除外で参照切れの書類や画像が出力されません。

- ごみ箱の顧客・車両・書類はキャンバス、未確定トレイ、顧客・車両の表示から抑制し、親顧客・親車両の明示除外も関連書類と画像へ伝播させます。
- 最終パッケージのスナップショット、document-links.json、manifest.json、出力サマリーへ、未確定トレイ由来と明示除外由来の書類件数、除外顧客、除外車両の理由を分離して保存します。確定状態は移動・復元時に解除します。
- 検証: dotnet build apps/companion/src/VehicleManagement.Companion/VehicleManagement.Companion.csproj --no-restore（成功）、git diff --check（成功）。実データでのごみ箱移動・復元とCSV目視確認は受入確認で行います。

### Gate 24: ABACUS書類種別、入庫区分、状態の復元

最初に実ファイルと既存CSV／UCSフィールドを読み取り専用で調査し、値とWebの列挙値の対応表を確定してから変換処理を実装します。

実装内容:

- 販売書類の見積書／請求書をABACUS値から判定します。
- 整備書類の見積書／請求書をABACUS値から判定します。
- 整備の入庫区分をABACUS値から判定します。
- 「点検」は「一般整備」に正規化します。
- 未知の入庫区分は「一般整備」にし、元の値と警告を残します。
- インポート基準日を完成パッケージ作成時または登録プレビュー時に一度だけ固定します。
- `書類日付 <= インポート基準日.AddMonths(-1)`を「完了」、それより新しい書類を「下書き」にします。
- 日付なし・不正値は「下書き」にし、警告件数へ含めます。
- APIはパッケージに保存された基準日と計算済み状態を再検証します。

受入条件:

- 既知の見積書と請求書がWebで正しい種別になります。
- ABACUSの点検書類がWebでは一般整備になります。
- 境界日の書類が完了、その翌日の書類が下書きになります。
- 同じ完成パッケージを後日再実行しても状態が変わりません。
- 不明値を無言で変換せず、レポートと詳細JSONへ残します。

実装記録:

- 補助アプリはABACUS販売・整備CSVの書類種別を見積書／請求書へ正規化し、整備の入庫区分を車検／板金／一般整備へ変換します。入庫区分の「点検」は一般整備として扱い、未知値は一般整備へフォールバックしつつ原文と警告を明細詳細JSON・備考・マニフェスト警告へ残します。
- 最終パッケージの`manifest.json`へ`importBaseDate`（実行環境のローカル日付）を保存し、販売は発行日、整備は出力された入庫日を基準に完了／下書きを一度だけ決定します。日付が空欄・不正な場合は下書きと警告にします。
- `ready/manifest.json`にも同じ基準日を伝播し、Web側のパッケージ検証で基準日の不一致を拒否します。基準日を持たない旧パッケージは従来のCSVステータスを使用する後方互換を維持します。
- APIは書類種別・入庫区分・状態を再正規化し、基準日がある場合はCSVの状態と計算結果の不一致を409で拒否します。登録済み書類の再実行検証にも種別・区分・状態を含め、同一パッケージの状態が変化しないことを保証します。

## 6. 推奨着手順と依存関係

基本順序は次のとおりです。

1. Gate 19の実データ受入確認
2. Gate 20: 車両情報なし書類の顧客画面対応
3. Gate 21: 紐づけ方法の永続化
4. Gate 22: 顧客なし車両
5. Gate 23: ごみ箱
6. Gate 24: 書類種別・入庫区分・状態（実装済み、受入確認）
7. Gate 25: 作業保存・再開
8. Gate 26: 検索・詳細
9. Gate 27: Web部分読み込み
10. Gate 28: おすすめ判定エンジン
11. Gate 29: マッチングUI
12. Gate 30: 総合検証

番号と着手順が一部前後するのは、Gate 25の共通作業状態をGate 28・29より先に固定するためです。Gate 29をGate 25より先に実装しません。

依存関係:

- Gate 20は既存の車両なし書類API基盤を利用し、他Gateから独立して着手できます。
- Gate 21の`linkMethod`はGate 25、28、29の保存形式の前提です。
- Gate 22と23の状態はGate 25のチェックポイントへ保存します。
- Gate 24はGate 19と同じ販売・整備データ経路へ触れるため、Gate 19受入確認後に回帰確認します。
- Gate 27はWeb表示モデルへ広く影響するため、Gate 20の特例表示を先に完成させてから移行します。
- Gate 28はUIに依存しない決定的なサービスとして先に実装し、Gate 29から利用します。
