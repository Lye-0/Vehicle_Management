# ABACUSローカル補助ソフト

ABACUSからのデータ移行など、Windows上でのみ実行できる処理をWebアプリから分離して担当する.NET 10 WPFアプリです。

## 実装済みの範囲

- WPF補助ソフトの起動
- LegacyHostの別プロセス起動・停止
- ユーザー限定Named Pipeによる疎通確認
- WPF終了時のLegacyHost終了
- 保存用ABACUSフォルダーの読取検査
- SHA-256検証付き作業用コピーの作成
- コピー後の保存用原本の再検証
- コピー側ABACUSの起動
- x64 LegacyHostからのUI Automation認識確認
- 販売・整備TABファイルの構造分析
- 検証マニフェストを使った既存作業用コピーの再検証
- コピー側ABACUSの画像画面に対するUI Automation要素診断
- ABACUSを画面側で終了した場合の終了状態再確認
- FileMaker ActiveXのx86登録・実行中インスタンスの読み取り診断
- `BackUp-5.fp5`のFileMaker 5.0ヘッダーとJPEG候補の読み取り診断
- 登録前候補パッケージの再検証と顧客・車両・書類グラフの読み取り専用プレビュー
- 保存用ABACUSフォルダー内の既存固定列CSVの自動検出と診断
- 固定列CSV候補作成後の自動再検証とグラフ表示

保存用原本は読み取り専用で扱い、ABACUSを起動するのは検証済みの作業用コピーだけです。

## 構成

```text
apps/companion/
├── VehicleManagement.Companion.slnx
└── src/
    ├── VehicleManagement.Companion/   WPF本体・プロセス管理
    ├── VehicleManagement.LegacyHost/  ABACUS処理を隔離するプロセス
    └── VehicleManagement.LocalProtocol/ Named Pipe通信契約
```

LegacyHostのビット数はまだ固定していません。Gate 2でx64 LegacyHostから32bit ABACUSをUI Automationできることを目視確認した後に決定します。

## 作業用コピーの安全策

- 必須ファイルの存在、ファイル数、合計サイズ、実行ファイル形式を検査します。
- リンクや再解析ポイントを拒否し、フォルダー外のファイルを読み込みません。
- 全ファイルのSHA-256を計算します。
- コピー先には毎回新しい`ABACUS-Work-yyyyMMdd-HHmmss`フォルダーを作り、既存ファイルを上書きしません。
- コピーした各ファイルを検証し、最後にコピー全体と保存用原本を再検査します。
- コピー先の隣に検証用の`.manifest.json`を保存します。
- キャンセルまたは失敗したコピーは起動対象にしません。

1GBを超えるファイルを複数回読み取るため、検査とコピーには時間がかかります。処理中もキャンセルできます。

## 書類データ分析

| ファイル | 内容 | 列数 | 主要な識別列（0始まり） |
| --- | --- | ---: | --- |
| `BackUp-2.tab` | 販売書類 | 102 | 顧客名0、登録番号13、車台番号22、書類番号51 |
| `BackUp-3.tab` | 整備書類 | 158 | 顧客名0、登録番号11、車台番号14、書類番号77 |

パーサーはShift-JISの不正バイト、列数違反、上限を超えるファイル・行・フィールド、未許可の制御文字、リンクを拒否します。ABACUS内で確認されたU+0004、U+000B、U+001Dだけは既知の内部区切りとして受け付け、後続変換で空白へ正規化します。

顧客名が空欄の行は構造エラーにはせず、取込候補から除外して件数を集計します。車両候補件数は車台番号、登録番号、顧客＋車両情報の順で保守的に算出しますが、この段階では顧客や車両を統合しません。

## 顧客・車両の紐付けプレビュー

顧客名だけでは自動統合しません。同じ正規化名の書類について、次のいずれかが一致する場合だけ同じ顧客候補にまとめます。

- 電話番号
- 住所
- 車台番号
- 車台番号との競合がない登録番号

同姓同名でも上記の根拠が一致しなければ別候補にし、競合一覧へ表示します。

車両は車台番号を最優先し、次に登録番号を使用します。同じ登録番号に異なる車台番号がある場合は、登録番号の再利用や入力差異の可能性があるため自動統合しません。同じ車両識別子が複数顧客に現れる場合も、名義変更・過去所有の可能性を含む競合として表示します。

このプレビューは候補と競合の確認専用であり、顧客・車両・書類をデータベースへ登録しません。

## ActiveXとfp5格納画像の診断

Gate 6Cで標準WindowsメニューとFileMakerの内部ウィンドウを確認した後、x86の別プロセスから`FMPRO.Application`の登録と実行中インスタンスだけを読み取ります。スクリプトの実行、メニュー操作、レコードの編集・保存は行いません。現在のABACUS Runtimeではx64・x86の両方で`FMPRO.Application`登録が確認できないため、ActiveX経由のエクスポートは採用しません。DLLの登録やシステムレジストリの変更も行いません。

Gate 6Dでは、ActiveXを使わずに保存用原本の`BackUp-5.fp5`を読み取り専用で検査します。FileMaker Pro 5.0のヘッダーとJPEG開始・終了マーカーをストリーム走査し、候補のファイル内位置、サイズ、読み取れる画像寸法だけを表示します。ファイルサイズは2GiB、JPEG候補は20,000件、候補1件は256MiB、画面表示は先頭100件までに制限します。画像本体の保存・顧客情報の表示・fp5の書き込みはこのGateでは行いません。

実機の保存用原本では、`BackUp-5.fp5`（約353MiB）からJPEG候補162件（合計約334MiB）が検出されました。これは画像の格納場所が存在することを示す診断結果であり、候補と車両を紐付ける仕様や元画像の安全な抽出方式は次のGateで確定します。

Gate 6Eでは、6Dの候補一覧から利用者が1件だけ選択し、ABACUSフォルダーの外側に新規JPGとして検証出力します。出力直前に現在のファイル範囲、JPEG開始・終了マーカー、標準JPEGのSOF/SOS/EOI構造、最大256MiB、最大5,000万画素、WPFのJPEGデコーダー、SHA-256を再検証します。FileMaker内部の分割ブロックを標準JPEGとして誤って保存しないよう、複数フレームやスキャン中の予期しないマーカーを検出した候補は保存せず、既存ファイルも上書きしません。実機の候補はこの構造検証を通過せず、灰色の仮画像を生成する結果になったため、元画像の抽出方式としては採用しません。実画像はGate 5D/5Eの画像表示ウィンドウの読み取りを利用するか、FileMakerコンテナの正式な解析方式を別途確定します。これは抽出方式の診断であり、車両との自動紐付けや一括出力ではありません。

## 車両画像の抽出準備

「画像抽出準備」タブでは、作成済みの`ABACUS-Work-*`フォルダーを隣接する検証マニフェストおよび保存用原本と照合し、許可条件を満たした場合だけ起動対象にします。

FileMaker Runtimeは、コピー側ABACUSを起動・操作しただけでも使用した`abx-cs-??.ucs`の管理情報を書き換えます。再利用時は保存用原本が作成時のハッシュを維持していること、ファイル構成・サイズが同一であること、他の全ファイルが原本と一致することを検証します。原本直下の`abx-cs-英数字2文字.ucs`だけは、サイズ不変、1ファイルあたり差分4,096バイト以内、全対象の合計差分16,384バイト以内に限定して許容します。`sbx-*`、実行ファイル、DLL、TABなどの変更は拒否します。

Gate 5Aでは、コピー側ABACUSで車両画像を手動表示した後、LegacyHostが標準UI Automationで認識できる要素を最大30件まで読み取り診断します。画像出力、キー入力、クリック、ABACUSレコードの変更は行いません。診断結果を確認してから、次のGateで対象要素に限定した1件抽出方式を決定します。

実機診断ではFileMakerのMDI子ウィンドウまでしかUI Automationに公開されず、画像フィールドを個別認識できませんでした。Gate 5Bでは利用者がABACUS上で車両画像を手動選択して`Ctrl+C`を行い、補助ソフトはクリップボードの形式名、標準画像として取得可能か、画像寸法、ファイル参照の件数と拡張子だけを診断します。画像本体の保存やプレビューはまだ行いません。

Gate 5Cでは、Gate 5Bで標準画像として診断した同一クリップボード内容を1件だけPNGへ変換します。最大5,000万画素・256MBに制限し、PNGとして再読込できることと寸法一致を保存前に検証します。保存用原本・作業用コピーの内部は保存先にできず、毎回新しいファイル名を作成して既存ファイルを上書きしません。

ABACUSでは画像フィールドを選択・コピーできないことが確認されたため、Gate 5Dでは`abx-cs-sk`のMDI子ウィンドウだけを対象に`PrintWindow`で表示内容を取得します。取得前にウィンドウが診断済みABACUSプロセスに属することを再検証します。これは画面表示解像度のPNGであり、FileMakerコンテナ内の元画像データではありません。

Gate 5Eでは、`PrintWindow`が返す右側・下側の未描画領域を除去します。末尾のほぼ黒一色の行・列を先に除外し、その内側にある非白色の描画範囲へ6ピクセルの余白を付けて切り出します。検出領域が64×64未満または元画像の5%未満の場合は異常検出として自動切り出しを適用しません。

Gate 5Fでは、非白色領域を単純にすべて包含せず、縦・横それぞれで最大の連続描画領域を画像本体として採用します。これにより画像本体から離れた右端のABACUS表示ラベルを除外します。また、画像上端の一定範囲だけを対象に、十分な高さを持つ高密度な操作領域とその直後の空白を検出できた場合に限り、サイズ切替ボタンを含む上部ツールバーを除外します。条件に一致しない通常画像ではツールバー除外を行いません。

Gate 5Gでは、保存した画像1件に対して利用者がABACUS画面で確認した車台番号または登録番号を入力し、画像と同じ保存先へ確認専用の`ABACUS-image-link-*.json`を新規作成します。車台番号を優先し、登録番号だけの場合は再利用の可能性があるため照合方式を`registration`として要確認扱いにします。画像ファイルのサイズ・SHA-256、画像寸法、原本・作業用コピーの検証済みフォルダー指紋を記録しますが、顧客・車両のデータベース登録、APIへのアップロード、ABACUSフォルダーへの書き込みは行いません。マニフェスト作成前に識別子を確認するダイアログを表示し、識別子が空欄の状態では作成できません。

Gate 5Hでは、画像保存先のマニフェストとABACUSの`syaryou.csv`／`syaryou2.csv`を読み取り専用で照合します。車両一覧は固定23列（顧客名0、メーカー11、車名12、型式17、車台番号18、登録番号19）としてShift-JIS・引用符・列数・行数・フィールド長・制御文字・ファイルSHA-256を検証します。車台番号と登録番号が同じ行に一致した場合だけ一致候補とし、登録番号だけ、短い・数字だけの車台番号、複数行一致、識別子競合、顧客名不一致、未一致は要確認または競合として自動登録候補から除外します。`syaryou.csv`と`syaryou2.csv`の行を顧客名で統合せず、重複候補をそのまま表示します。画像ファイルのSHA-256も再検証し、マニフェストや画像が改変されている場合は不正扱いにします。この段階でもデータベース登録・APIへのアップロード・CSVへの書き込みは行いません。

Gate 5Iでは、Gate 5Hで一意の候補になった「一致」または「要確認」の行を利用者が目視確認し、選択した場合だけ確認済み証跡`ABACUS-image-approval-*.json`を画像保存先へ新規作成します。承認直前にマニフェスト・画像・車両一覧CSVを再読込し、画像SHA-256、マニフェストSHA-256、CSVファイルSHA-256、CSV行番号と行内容を再検証するため、画面表示後の差し替えは承認されません。証跡は原子的に作成し、同じマニフェストの二重承認を拒否します。これは人による確認事実を残す段階であり、顧客・車両の登録、APIへのアップロード、ABACUSフォルダーへの書き込みは引き続き行いません。

Gate 5Jでは、`human-reviewed`の確認済み証跡を再検証し、確認済み画像と対応する`syaryou.csv`／`syaryou2.csv`の行だけを新しい`ABACUS-Image-Registration-Preview-*`フォルダーへコピーします。`manifest.json`には確認済み証跡・画像・CSV行のハッシュ、CSVファイル名・行番号、車両識別子、顧客名、画像相対パスを登録前候補として保存します。顧客名だけで同姓同名を統合せず、候補IDは証跡・マニフェスト・CSV行から決定します。画像コピー後とマニフェスト保存後に再読込検証を行いますが、この段階でも顧客ID・車両IDの解決、データベース登録、API送信、ObjectStorageへのアップロード、ABACUSフォルダーへの書き込みは行いません。

Gate 5Kでは、Gate 5Jの`ABACUS-Image-Registration-Preview-*`を入力として、既存WebインポートAPIの見出しに合わせたUTF-8（BOM付き）`customers.csv`と`vehicles.csv`、画像対応表`image-attachments.json`を新しい`ABACUS-Web-Import-Preview-*`へ作成します。ABACUSの元号年・日付・数値・記録簿表記は、APIが受け付ける値へ変換できた場合だけ正規化し、原文と出典を備考へ残します。候補ごとに決定的な仮の顧客ID・顧客番号・車両IDを発行し、顧客名による既存顧客への自動照合や同姓同名の自動統合は行いません。同じ顧客名が複数候補に現れる場合は、複数車両か同姓同名かを手動確認する警告をマニフェストへ記録します。CSVの作成後もWeb API送信、顧客・車両の登録、画像アップロードは行わず、画像対応表は次段階の手動アップロード用です。

Gate 5Lでは、Gate 5Kの候補CSVを再検証して顧客・車両の一覧を表示し、顧客グループキーを人が確認・編集できるようにします。初期値は候補ごとに別顧客です。同じ顧客に複数車両があると確認した行だけ同じキーへ変更し、異なる顧客名を同じキーへ設定する操作は拒否します。確定時には`ABACUS-Web-Import-Mapping-*`フォルダーへ`mapping.json`（`human-reviewed`）を新規作成し、入力パッケージのSHA-256、候補ID、車両CSV行、画像、顧客グループキー、判断理由を記録します。この段階でもCSVの書換え、顧客・車両の登録、API送信、画像アップロードは行いません。

Gate 5Mでは、Gate 5Lの`human-reviewed`対応付け証跡と入力候補パッケージを再検証し、`ABACUS-Web-Import-Registration-Preview-*`フォルダーへ登録前パッケージを作成します。顧客グループごとに決定的な顧客ID・顧客番号を発行し、同じ顧客に複数車両がある場合は顧客CSVを1行、車両CSVを複数行へ変換します。車両ID、画像、画像SHA-256、候補ID、対応付け判断、CSV行の出典は保持し、`image-attachments.json`の顧客ID・車両IDも出力後の値へ更新します。出力マニフェストは対応付け証跡と入力候補マニフェストのSHA-256を記録し、CSV・画像・JSONを再読込検証します。この段階でもWeb API、D1、Object Storage、ABACUSフォルダーへの接続・書込は行いません。

Gate 5Nでは、Webアプリの設定画面からGate 5Mの`ABACUS-Web-Import-Registration-Preview-*`フォルダーを選択し、ブラウザー内でマニフェスト、全ファイルのサイズ・SHA-256、CSVのUTF-8・見出し・列数、画像対応表の参照先を再検証します。検証に合格した`customers.csv`と`vehicles.csv`だけを既存Web APIの`preview`エンドポイントへ送信し、API側の入力エラーと件数を表示します。`commit`エンドポイントは呼び出さず、顧客・車両の登録、画像アップロード、D1・Object Storageへの書込は行いません。フォルダー内の画像はローカル検証と対応表確認のために読み取るだけで、Webへ送信しません。実登録の前に、次段階で人が最終確認する導線を設けます。

Gate 5Oでは、Gate 5Nのプレビューと確認文字列`ABACUS登録を実行`が一致した場合だけ、管理者向けの登録APIを呼び出します。サーバー側でもマニフェストのSHA-256、固定ヘッダー・列数・値形式、顧客の車両台数、画像対応表、既存IDの内容を再検証します。顧客と車両はD1の一括処理で同時に登録し、同じ仮IDの内容が完全一致する再試行は冪等に更新扱いとします。画像は20MB以下のPNG/JPEGを1件ずつSHA-256・シグネチャ検証してB2へ保存し、表示・ダウンロード用ファイル名には`車検証_`を先頭に付けます。途中で失敗した画像だけ同じパッケージから再試行できます。画像アップロードは顧客・車両のD1登録とは別処理であり、ABACUS原本は変更しません。

## 永続ローカル移行パッケージ

Gate 6Aでは、利用者が選択した通常フォルダーへ`ABACUS-Migration-Preview-*`フォルダーを新規作成します。開発中のWorkersプロセスが持つ一時ファイルシステムは永続保存先として扱いません。将来、開発用または本番用ObjectStorageへ接続する前段として、補助ソフト側に永続成果物の境界を置きます。

この段階で出力する`manifest.json`は、販売・整備TABファイルのファイル名、サイズ、SHA-256と、顧客・車両・書類候補、除外、競合の集計だけを含みます。顧客名・住所・電話番号などの行データ、画像、変換済みデータは含めず、`status`を`preview-only`、`dataFiles`と`imageFiles`を空配列に固定します。書込後にマニフェストを再読込して内容を検証し、既存ファイルは上書きしません。

Gate 6Bでは、ABACUSが出力する見出しなし固定列CSVを読み取り専用で診断します。販売は33列、整備は29列、車両一覧は23列として扱い、Shift-JISの不正バイト、引用符、列数、5MB・5,000行の上限、フィールド長、制御文字、主要な必須値を検証します。`syaryou.csv`と`syaryou2.csv`が同時に存在する場合、同一車両の重複可能性があるため自動結合しません。この段階では登録用データを出力しません。

Gate 6Bの診断画面では、各CSVの先頭データ行を0始まりの列番号付きで表示します。金額・明細・日付の位置を人が確認した後、車両一覧が1ファイルだけで診断に合格した場合に限り、「固定列CSVから登録前候補を作成」を実行できます。作成先には`ABACUS-Export-Import-Preview-*`を新規作成し、`customers.csv`、`vehicles.csv`、`sales.csv`、`maintenance.csv`、`manifest.json`を保存します。これは既存Webインポート形式に合わせた読み取り専用の候補であり、Web API、D1、Object Storage、画像アップロード、ABACUS原本への書き込みは行いません。

候補化では、車両一覧の各行を独立した車両候補として扱います。顧客名だけでは統合せず、住所がある場合は顧客名と住所を候補キーに含め、住所のない行には出典ファイル名と行番号を含めます。書類の車台番号・登録番号が車両一覧の1行に一致し、顧客名（および双方に住所がある場合の住所）も矛盾しない場合だけ車両へ仮紐付けします。複数候補、識別子競合、顧客情報の不一致は「要確認」として自動紐付けを保留し、整備書類は車両が一意に確定しない行を候補CSVから除外します。顧客名が空欄の行はエラーにせず無視し、除外件数を画面とマニフェストへ記録します。販売・整備の税額と明細列は、ABACUSの確定位置を別途確認するまで未確定として警告を残します。

候補パッケージ作成後は「候補パッケージを再検証」から同じフォルダーを読み込み、マニフェストと4つの候補CSVを再検証できます。ファイルの存在、リンク属性、UTF-8、固定見出し、列数、行数、サイズ、SHA-256が一致しない場合は一覧を表示せず停止します。合格後は出典CSVの行番号、顧客名、車両名、書類番号、判定、判定理由を一覧で確認できます。これは最終的なグラフ型の手動紐付けUIへ渡す前の再検証段階であり、現時点では候補の編集や登録は行いません。

再検証に合格すると「顧客・車両・書類のグラフ型確認」が表示されます。左側で顧客を選ぶと、顧客から車両、車両から書類へ関係をたどれます。右側には選択した顧客・車両・書類の詳細と判定根拠を表示し、画面下部には未確定車両・未確定販売書類・未確定整備書類を分けて表示します。車両右側と書類左側の丸いノードが接続点です。マニフェストが一意一致と判定した書類は緑色の実線、手動仮紐付けは青色の点線、未接続は赤色の点線、顧客にだけ紐付いて車両が未確定の書類は橙色の点線で区別します。書類ブロックまたは書類ノードを別の車両へドラッグすると、画面上だけの手動仮紐付けとして接続先を変更できます。車両ノードから書類ノードへドラッグしても同じ変更ができます。書類左側のノード直後にある「×」でノード接続を切ると、キャンバス上の未接続状態になります。未接続・車両未確定書類は車両へ接続するか、書類ブロックを未確定トレイへ移動してください。トレイへ移した書類は、元々自動確定だった場合も一時的にキャンバスから外れます。ブロックをドラッグすると半透明のプレビューが表示され、無効な場所にドロップした場合は自動整列位置へ戻ります。元の候補CSV、マニフェスト、ABACUS原本は変更せず、画面を再読込すると仮紐付けは破棄されます。

顧客統合、書類操作、ノード操作がすべて完了した後、画面下部の「インポート内容を確定」を押すと全体を確定できます。未確定トレイへ残っている販売・整備書類がある場合は、その最終確定時に種類別の件数を警告ダイアログで表示します。確定を選ぶと、その書類は今回のインポート対象から除外する状態として画面上で記録し、確定後に操作を変更した場合は確定状態と除外状態を解除します。顧客グループごとの「キャンバスを承認」は統合表示を確定するだけで、未確定トレイの除外は行いません。元の候補CSV、マニフェスト、ABACUS原本は変更しません。現在のグラフ画面は登録前の確認段階であり、除外一覧を実際の書類CSV/API登録へ引き継ぐ処理は、書類登録パッケージを追加する次段階で実装します。

顧客一覧はグループ候補を親、統合元顧客を1段インデントした階層で表示します。通常顧客には展開用のボックスを表示せず、一覧幅と右側の余白を確保して長い顧客名・住所がスクロールバーに隠れないようにしています。同じ正規化顧客名の候補は統合候補として自動的にグループ化されます。候補とプレビュー保存済みは橙色、キャンバス承認済みは青色です。顧客カードを別の顧客カードまたは候補グループへドラッグすると、名前が異なる顧客も統合候補へ追加できます。ドラッグ中に一覧の上下端へ近づくと一覧が自動スクロールし、解除領域は一覧の上部に一時表示されるため、一覧末尾への移動で誤スクロールしません。候補グループはドラッグ直後からキャンバスへ仮想顧客として表示され、右側の「顧客情報をプレビュー」で電話・メール・住所などの採用値と統合後の顧客名を選択します。プレビュー保存後も候補は橙色のままで、キャンバスを確認して「キャンバスを承認」を押した時点で左一覧のグループが青色の承認済みになります。元の顧客ID・候補CSV・データベース・APIは変更しません。

Gate 8Aでは、グラフの顧客統合・ノード操作・書類操作をすべて完了して「インポート内容を確定」した後、画面下部の「確定内容から登録前パッケージを作成」を実行できます。保存先の外側へ新規 `ABACUS-Graph-Import-Registration-Preview-*` フォルダーを作成し、確定後の `customers.csv`、`vehicles.csv`、`sales.csv`、`maintenance.csv`、`document-links.json`、`manifest.json` を出力します。最終確定時に未確定トレイへ残っていた書類は除外キーとしてマニフェストへ記録し、4つのCSVへは出力しません。顧客が一意に判定できる車両情報のない書類は、書類CSVの車両列を空欄にして `document-links.json` の `vehicleless: true` として出力します。これはWeb側で車両を「なし」と表示する互換性用の特例であり、この段階ではWeb API、D1、Object Storage、画像アップロード、ABACUS原本への書き込みは行いません。次のGateでこのマニフェストと特例書類をWeb側のプレビュー・登録APIへ接続します。

Gate 8Cでは、Gate 8AのパッケージをWeb側で再検証し、確認文字列が一致した場合だけ顧客・車両・販売書類・整備書類を登録します。ABACUSでは同じ種類の書類番号が別行で再利用されることがあるため、登録時は書類IDを保持したまま重複番号へ決定的な枝番（例：`1203-2`）を付け、元の番号と出典を備考へ残します。ABACUSで小計・合計が空欄の書類は、登録用の金額を0（小計未設定時は消費税を加えた合計）として補正し、未設定であることを備考へ残します。顧客・車両・書類の登録は同一のD1 batchで行い、車両情報なし書類は顧客だけへ保存します。通常のWeb画面から作成する書類は引き続き車両必須です。

Gate 8Dでは、登録済み書類の詳細JSONに保存したABACUS出典・車両なしフラグを販売・整備書類APIの表示モデルへ引き継ぎます。Web画面では該当書類に「ABACUS・車両なし」と出典を表示し、車両欄は「なし」として扱います。通常のWeb書類作成は車両必須のまま維持し、ABACUS互換の車両なし書類だけを顧客に紐付いた特例として表示します。元のABACUSデータ、登録済み書類の詳細、画像アップロード処理は変更しません。

Gate 8Eでは、保存用ABACUSフォルダーを選択したとき、フォルダー直下と深さ3までの子フォルダーから`hanbai.csv`、`seibi.csv`、`syaryou.csv`、`syaryou2.csv`を読み取り専用で自動検出します。候補フォルダーが1件だけの場合はそのフォルダーを選択して固定列診断まで自動実行します。複数候補、走査上限到達、未検出の場合は自動選択せず、画面に理由を表示して手動選択へ戻します。再解析ポイントなどの再パースは辿らず、元のABACUSフォルダーとCSVは変更しません。自動検出後も、車両一覧が複数ファイルの場合の全件選択や、列サンプルの目視確認は従来どおり利用者が行います。

Gate 8Fでは、固定列CSVから登録前候補パッケージを作成した直後に、保存済みマニフェストと候補CSVを自動で再検証し、合格した場合は顧客・車両・書類のグラフを表示します。候補パッケージの保存先選択は利用者が行いますが、同じパッケージをもう一度選択する操作は省略できます。再検証に失敗した場合はグラフを表示せず、従来の「候補パッケージを再検証」から手動で再試行できます。登録・API送信・画像アップロード・元CSVやABACUSフォルダーへの書き込みは行いません。

Gate 8Gでは、グラフの最終確定後に画面へ次の操作を明示します。確定前は「インポート内容を確定」、確定後は「確定内容から登録前パッケージを作成」の順に案内し、パッケージ作成が完了すると作成フォルダーを開く操作と、Webアプリの「ABACUS登録前パッケージをプレビュー」でそのフォルダーを選択する案内を表示します。フォルダーを開く操作はローカルのエクスプローラーを起動するだけで、Web API、D1、画像アップロード、ABACUS原本への書き込みは行いません。Web側で確認文字列を入力するまでは登録処理は実行されません。

Gate 9Aでは、補助ソフトの「ABACUSインポート」タブを通常操作の入口として整理します。保存用ABACUSフォルダーを選択すると、既存の自動CSV検出と固定列診断を自動実行し、合格後は「解析してキャンパスを表示」から候補パッケージの保存先を1回選ぶだけで候補作成・再検証・グラフ表示まで連続して実行します。候補パッケージの再検証が完了すると同じページ内のグラフ見出しへ自動移動し、顧客統合・書類紐付け・ノード操作を開始できます。6A〜6Bの詳細表、候補パッケージの手動再検証、ABACUS診断は「詳細診断（必要な場合のみ）」へ折りたたみ、トラブル時の読み取り専用確認機能として残します。元のABACUSフォルダー、CSV、Web API、D1、画像アップロードは変更しません。画像抽出経路を同じ通常画面へ統合する作業は、画像の登録前パッケージへの取り込み方式を確定した後の次段階で行います。

Gate 9Bでは、従来「画像抽出準備」タブにあった画像診断、表示画像の保存、車両識別子との照合、確認済み証跡、画像登録前パッケージ、Webインポート候補作成、顧客対応付け、Web登録前パッケージ作成のコントロールを、ABACUSインポートページ内の「画像・Web登録準備（必要な場合のみ）」へ移します。既存の処理・検証・書き込み禁止境界はそのまま再利用し、通常は折りたたんでキャンパス操作を妨げません。画像処理が必要な場合だけ同じページで展開でき、画像処理のために別タブへ移動する必要はありません。旧タブは表示対象から外しますが、画像コントロールのイベントと読み取り専用検証は変更しません。画像をグラフ確定パッケージへ自動的に含める処理は、次のGateで対応関係と再検証方式を確定してから追加します。

Gate 9Cでは、Gate 8Aのグラフ確定パッケージ作成時に、Gate 5Jの確認済み画像登録前パッケージを任意で指定できます。画像登録前パッケージが指定された場合、補助ソフトは画像登録前マニフェスト、画像本体、画像SHA-256を再読込し、車台番号・登録番号をグラフ確定後の車両へ一意に再照合します。照合不能、複数一致、パス・拡張子・サイズ・ハッシュの不正が1件でもある場合は、顧客・車両・書類の登録前パッケージ自体を作成しません。照合済み画像はグラフ確定パッケージの`images/`へコピーし、`manifest.json`の`imageFiles`と`summary.imageCount`、`image-attachments.json`へ顧客ID・車両ID・相対パス・SHA-256・Content-Typeを記録します。画像を指定しない従来の画像なしパッケージも引き続き作成できます。

Gate 9Dでは、Webの「ABACUS登録前パッケージをプレビュー」でGate 9Cのフォルダーを選択すると、CSV・書類対応表に加えて画像本体、`imageFiles`、`image-attachments.json`の件数・サイズ・SHA-256・顧客/車両参照をブラウザー内で再検証します。登録確認後、まず顧客・車両・書類・車両なし書類を既存のグラフ確定登録APIで登録し、その応答が成功した場合だけ、同じパッケージ内の画像を既存画像アップロードAPIへ1件ずつ送信します。画像の送信に失敗した場合は失敗した相対パスを画面へ表示し、顧客・車両・書類の登録結果を取り消さずに画像だけ再試行できる境界とします。画像アップロード時の表示名には従来どおり`車検証_`を付け、元のABACUSフォルダーや登録前パッケージは変更しません。

## Gate 10: ABACUS画像の一括準備と自動マッピング

Gate 10では、ABACUSインポートページ内の「画像・Web登録準備（必要な場合のみ）」に、画像の一括処理入口を追加しました。保存用ABACUSフォルダーを選択した状態で保存先を一度選び、「画像を一括抽出・照合」を押すと、フォルダー内の標準PNG/JPEGを再帰的に読み取り、サイズ・デコード・画素数・SHA-256を検証します。ファイル名の車台番号・登録番号を`syaryou.csv`／`syaryou2.csv`の車両行へ照合し、1行だけに一致した標準画像を登録前候補へ含めます。さらに、保存用ABACUSフォルダー直下の`abx-*.ucs`を読み取り専用で走査し、内部のJPEG候補を診断レポートへ記録しますが、UCS内部の生データは実画像として保存しません。

複数候補、未照合、壊れた標準画像は自動登録候補にせず、画面の一覧と同パッケージの`image-batch-report.json`へ判定理由を記録します。標準画像は`images/`へまとめて保存するため、ユーザーは個別に保存し直さずレポートの相対パスから確認できます。同一内容の標準画像はSHA-256でグループ化し、最も確度の高い1件だけをパッケージへ保存します。異なる車両へ同じSHA-256が対応する場合は自動登録せず「同一画像・複数車両」の要確認1件にまとめ、重複除外件数と元候補をレポートへ残します。UCS内部候補は復号できた場合でも保存・登録せず「抽出不可」としてレポートに残します。登録前候補は既存の`abacus-image-registration-preview`形式で一意照合済み標準画像だけを作成し、グラフ確定時の画像登録前パッケージへ自動設定されます。元のABACUSフォルダー、UCS、CSV、既存の画像ファイルは変更せず、保存先が入力フォルダーの内部になる場合は処理を中止します。

FileMakerの`*.ucs`／`BackUp-5.fp5`は内部コンテナ形式です。Gate 10は原本を推測分割・書換えせず、標準画像だけを一時パッケージへコピーします。UCS候補は診断レポートへ残しますが、反復するFileMaker内部ブロックヘッダー、壊れたマーカー、均一色の仮画像として復号された候補はすべて「抽出不可」として保存しません。UCSレコード領域の車台番号が複数候補または見つからない候補も`image-batch-report.json`の「要確認」「未照合」に残し、自動登録候補へは含めません。実画像を一括取得するには、ABACUSの画像表示画面をキャプチャする経路（Gate 5D/5Eの方式を一括化）またはFileMakerコンテナの正式な解析方式を別Gateで実装する必要があります。これにより、誤った車両への自動紐付け、灰色・ノイズ画像の登録、原本破損を防ぎます。

## 今後の確定方針（Gate 11以降）

この節は、Gate 10までの実機検証を踏まえて合意した最終構成です。今後の実装ではこの節を優先し、過去Gateの診断UIや中間成果物をそのまま通常利用者向けの最終導線にはしません。

### 完成版補助ソフトの画面構成

補助ソフトに通常利用者向けの完成タブを追加し、最終的にはこのタブを起動時のデフォルト表示にします。既存の検査、診断、個別パッケージ作成などのタブは削除せず、「詳細調査を表示」のような明示的な操作を行った場合だけ表示する診断用機能として残します。

```text
        └── image-acquisition-report.json
```

`work/`は検証済み作業用コピー、中間生成物、中断再開用チェックポイント、ローカル診断ログを置く領域であり、Webインポート対象にはしません。削除しても完成品の検証に影響しない再生成可能な領域として扱います。

`ready/`はWebへ渡す完成品だけを置く領域です。作成途中のファイルを直接`ready/`へ保存せず、`work/`内で生成と再検証を完了した後に完成状態へ切り替えます。不完全なパッケージや検証に失敗したパッケージを`ready`として扱いません。

ルートの`abacus-import.json`はパッケージ識別子、形式バージョン、完成品の相対パスを持ちます。Webアプリはフォルダー名だけに依存せず、このファイルから`ready/`を特定します。`ready/manifest.json`には少なくとも次を記録します。

- パッケージ形式バージョン、パッケージID、`ready`状態、作成日時
- 元ABACUSフォルダーの検証済み指紋
- 全CSV、JSON、画像の相対パス、サイズ、SHA-256
- 顧客、車両、販売書類、整備書類、画像、除外、未解決の件数
- 選択した画像取得方式と画像取得レポート

Web側では利用者が`ABACUS-Import-*`ルート全体を選択できますが、クライアントは`abacus-import.json`を検証し、`ready/`だけを検証・送信します。`work/`は列挙後のインポート対象から除外し、アップロードしません。

### CSVを起点とするデータ解析

現段階では、ABACUSフォルダー内に既に存在する`hanbai.csv`、`seibi.csv`、`syaryou.csv`、`syaryou2.csv`を自動検出して解析する方式を採用します。CSVが存在しない場合や古い場合にABACUSを自動操作してCSVを再出力する機能は、この確定方針の主対象には含めず将来拡張とします。

顧客名が空欄の書類・車両行はインポート候補から除外し、除外件数と理由をレポートに残します。利用者が全ての顧客統合、書類操作、ノード操作を終えて「インポート内容を確定」した時点で未確定トレイに残っている書類も、警告と種類別件数を表示したうえでインポート対象から除外します。

顧客が一意に確定している一方で車両情報を持たないABACUS書類は、互換性のため顧客へ直接紐付ける特例として完成パッケージへ含めます。Webでは顧客の所有車両一覧に「車両情報のない書類」ブロックを表示し、販売および車検・点検・一般の一覧では車両を「なし」と表示します。通常のWeb画面から車両なし書類を新規作成する機能は追加しません。

### 調査報告を踏まえた画像抽出の新方針

実ファイルを解析した調査報告では、`abx-cs-sk.ucs`をFileMaker Pro 5.0のコンテナとして解釈し、1024バイトセクター、前後リンク、FileMakerのトークン列、画像セグメントの連結を復元する方式が示されています。報告上は、153件のJPEG候補について、長さ検証・SOI/EOI検証・画素デコード・SHA-256計算が153件すべて成功し、車検証画像として目視できるサンプルも確認されています。これは、従来の`FF D8`から`FF D9`までの生 carve とは異なる、検証可能な方式です。

ただし、報告の方式はまだ本リポジトリへ統合されておらず、画像と`syaryou.csv`の車両を完全に対応付ける方法も未確定です。そのため、次の条件を満たすまで「実装済み」とは扱いません。

- FileMaker Pro 5.0形式、1024バイトセクター、リンク順、トークン列、分割セグメントを読み取り専用で再現できること
- 抽出画像のファイル長、JPEG構造、デコード、SHA-256が一致すること
- 画像と車両の対応付けを、内部関係または車台番号・登録番号の一意一致で説明できること
- 153件と車両一覧の件数差を、行順や推測で埋めず、未一致・複数候補として安全に扱えること
- 保存用原本、UCS、CSVへ一切書き込まず、`work/`内で再実行できること

主ルートは次のとおりです。

1. ABACUSフォルダーと生成物の親フォルダーを確定する
2. 作業用コピーを作成し、CSVとFP5/UCSを読み取り検査する
3. FileMakerコンテナをセクター／リンク／トークン単位で復元する
4. JPEGを完全デコードし、`work/`へ一時保存する
5. 車台番号・登録番号・内部関係を照合し、一意一致だけを登録候補へ進める
6. 未一致・複数候補・壊れた画像は要確認または抽出不可としてレポートへ残す
7. グラフ確定後、検証済み画像だけを`ready/images/`へコピーする

入力欄へパスを入力しただけでは重い処理を開始せず、両フォルダーを確定して「解析を開始」を押した時点で一括解析を始めます。通常画面では、利用者は方式を選ばず、CSV解析・画像抽出・照合の進捗と要確認件数だけを確認します。

### 画像取得方式の扱い

FP5コンテナ復元方式を主方式とし、従来の画面移動型取得は、主方式が必要な画像を取得できない場合のフォールバック候補として残します。UCSの単純なJPEG carving、灰色・均一色・ノイズ画像、検証不能な候補は、実画像として保存・登録しません。

画面移動型フォールバックを実装する場合も、座標と固定待機時間だけに依存せず、画面状態の分類、遷移確認、車両識別子の照合、保存画像の内容検証、中断・再開・失敗車両の再試行を備えた状態機械にします。主方式の失敗時だけ「詳細調査」から起動できるようにし、通常導線へ方式選択を戻しません。

### Gate 11〜18の実装順

#### Gate 11: 成果物フォルダー契約（実装済み）

- `work/`と`ready/`を持つ処理ルートを作成
- `abacus-import.json`と`ready/manifest.json`のスキーマを確定
- 作成途中と完成済みを分離し、原子的に完成状態へ移行
- 中断再開用チェックポイントを定義
- `work/`をWebインポート対象から除外

目視確認では、選択した生成先に2領域が作られ、`work/`の中間ファイルが`ready/`へ混入しないことを確認します。

#### Gate 12: 完成タブの基盤統合（実装済み）

- ABACUSフォルダーと生成物親フォルダーの選択
- Gate 11の処理ルート作成と現在の作業状態の表示
- 既存の顧客・車両・書類紐付けキャンバスを同じページへ統合
- 画像取得方式、進捗、停止・再開を接続する共通UIと状態契約を用意
- インポート内容の確定、完成パッケージ作成、Web側の次操作案内を同じページへ配置
- 既存タブを「詳細調査」操作の配下へ移動
- 完成タブを起動時のデフォルトへ変更

このGateでは、未完成の画像取得処理を見せかけで動かしません。既存処理を完成タブから呼び出せるようにし、Gate 13以降の画像取得エンジンを後から画面移植なしで接続できる境界までを実装します。

#### Gate 13: FP5コンテナ復元の実証

- 実ファイルの作業用コピーを入力にする読み取り専用パーサーを作成
- FileMaker Pro 5.0ヘッダー、1024バイトセクター、前後リンク、トークン列を検証
- 既知の1画像を復元し、ファイル長、SOI/EOI、デコード、寸法、SHA-256を確認
- 既知画像を複数件へ拡張し、壊れた候補を保存せずレポートへ分離

目視確認では、復元された車検証画像が灰色・ノイズ状ではなく読めること、原本フォルダーに新規ファイルが作られていないことを確認します。ここではまだ顧客・車両・Web APIへの登録を行いません。

#### Gate 14: 全画像抽出と車両対応付け

- 全UCS／FP5コンテナを走査し、抽出画像を`work/`へ保存
- 内部の車両関係を最優先で解析
- 内部関係が得られない場合は車台番号と登録番号の同一行完全一致を使用
- 一意な登録番号だけの一致は要確認扱いとし、行順による対応付けは行わない
- 153件対154台など件数差、画像なし、複数候補、重複SHA-256、抽出不可を分類
- チェックポイント、再開、キャンセル、失敗候補だけの再試行を実装

検証は既知サンプル、少数件、全件の順に行い、抽出件数・照合件数・要確認件数・除外件数をレポートと一致させます。自動登録候補は「根拠を説明できる一意一致」だけに限定します。

#### Gate 15: 完成タブへの主方式統合

- ABACUSフォルダーと生成物親フォルダーの確定後、「解析を開始」でCSV解析とFP5画像抽出を連続実行
- 画像取得方式の選択UIを通常画面から削除し、進捗・結果・要確認だけを表示
- 抽出画像、顧客・車両・書類グラフ、手動紐付け、統合、`ready/`作成を一つの導線へ接続
- 画像の対応付け根拠、SHA-256、抽出不可・未一致・複数候補を詳細調査から確認可能にする
- グラフ確定時に検証済み画像を完成品へ取り込み、未確定トレイの除外警告と同じ確定境界で扱う

このGateの目標は、利用者が「フォルダー選択 → 解析開始 → キャンバス確認・修正 → インポート内容を確定 → 完成品フォルダーをWebへ渡す」だけで進めることです。

#### Gate 16: 画面移動型画像取得フォールバック（条件付き）

- Gate 13・14でFP5方式が全件または実運用上必要な範囲を満たさない場合だけ実装
- ABACUSのメニュー、車両一覧、車両詳細、拡大画像を状態機械で遷移
- 画面表示画像を取得し、車台番号・登録番号の照合と画像内容検証を行う
- 中断・再開、キャンセル、失敗車両の再試行、取得経路の証跡を実装
- 完成タブの「詳細調査」または失敗候補の再取得からのみ起動

Gate 13・14の合格条件を満たし、必要な画像をFP5方式で安全に抽出・照合できた場合、Gate 16は実装しません。画面移動方式の既存診断コードは詳細調査用として残しても、完成版の通常導線には含めません。

#### Gate 17: Web側のフォルダー一括受入

- `ABACUS-Import-*`ルートをフォルダー単位で選択
- `abacus-import.json`から`ready/`を特定し、`work/`を送信対象外にする
- マニフェスト、全ファイル、SHA-256、参照関係をブラウザーとAPIで再検証
- 顧客、車両、書類、車両なし書類、画像、除外件数を登録前にプレビュー
- 最終確認後に登録し、画像失敗だけを再試行可能にする

#### Gate 18: 総合検証

- バックアップ復元後の繰り返しインポート
- 同じパッケージの再実行に対する冪等性
- 処理中断と再開
- 未確定トレイの除外警告
- 車両情報のない書類
- 同姓同名・手動統合・複数車両
- 画像なし車両、重複画像、取得失敗
- 大量データ時の時間、メモリ、進捗表示
- 保存用ABACUS原本が変更されていないこと

Gate 11・12で成果物境界と完成タブの基盤を固定し、Gate 13・14でFP5コンテナ復元と車両対応付けを実証します。主方式が成立した場合はGate 15で画像抽出を完成タブへ直接統合し、画像取得方式の選択UIは置きません。主方式が成立しない場合だけGate 16の画面移動型フォールバックを追加し、成立した場合はGate 16をスキップできます。その後、Gate 17でWeb側のフォルダー一括受入、Gate 18で反復・復元・大量データを含む総合検証を行います。

GUIを使わず、個人情報を出力せずに集計だけを確認する場合は次を使用します。

```powershell
dotnet run --project apps/companion/src/VehicleManagement.AbacusImport.Cli/VehicleManagement.AbacusImport.Cli.csproj -- "<ABACUSフォルダー>"
```

固定列CSVの診断結果と先頭データ行の列サンプルを確認する場合は、次を使用します。出力はローカルの端末に表示するだけで、CSVやABACUSフォルダーは変更しません。

```powershell
dotnet run --project apps/companion/src/VehicleManagement.AbacusImport.Cli/VehicleManagement.AbacusImport.Cli.csproj -- --legacy-export "<ABACUSのCSVフォルダー>"
```

## ビルドと起動

リポジトリルートから実行します。

```powershell
dotnet build apps/companion/VehicleManagement.Companion.slnx
dotnet run --project apps/companion/src/VehicleManagement.Companion/VehicleManagement.Companion.csproj
```

GUIを表示せず通信・終了処理を検証する場合は、ビルド後の実行ファイルに`--self-test`を指定します。

```powershell
apps/companion/src/VehicleManagement.Companion/bin/Debug/net10.0-windows/VehicleManagement.Companion.exe --self-test
```

終了コード`0`なら、LegacyHostの起動、ハンドシェイク、ping、正常終了に成功しています。
